= Estate-wide Mathematical Knowledge Architecture — working proposal

Status: *unratified architectural brief*. Preserved from the former Mathesis root file `estate-mathematical-architecture` for discoverability and historical provenance. It is not the adopted architecture, a verified implementation plan, or a source of estate-wide proof grades.

The controlling estate proof policy lives at https://github.com/metadatastician/standards/blob/main/3-practice/PROOF-POLICY.adoc[PROOF-POLICY]. Mathesis's live census and first atlas slice are described in link:../../README.adoc[the README] and link:../atlas/README.adoc[the atlas README]. In particular, any conflicting grade definitions, tool flags, integration claims, or proposed storage arrangements below require explicit review, not silent adoption.

[IMPORTANT]
.§5 grades superseded: Proof Witness Grades (owner ruling 2026-11-04)
====
The grade ladder in §5–§6 below was adopted as estate policy, with
corrections, as *Proof Witness Grades* (PWG) in
https://github.com/metadatastician/standards/blob/main/3-practice/PROOF-POLICY.adoc#proof-witness-grades[PROOF-POLICY §8]
(standards#1410, which closes mathesis#11). That section governs. The text
below is kept unedited as provenance. Read it with this map:

[cols="1,1,3",options="header"]
|===
|Brief |Policy |What changed

|Grade 3
|`PWG-3`
|The flags must be in force *and* recorded under the canonical
`agda --safe --without-K --cubical-compatible` (PROOF-POLICY §2.1).
`--erasure` is not part of it. Full `--cubical` needs the separately
reviewed proof profile of §2.1.

|Grade 2i
|`PWG-2i`
|One recheck leg (Rocq or Lean) counts. A leg counts only when it is
kernel-checked *and* its statement correspondence is `RECONCILED` (§2.2),
whether it was transported or re-proved. A rung is not a discharge: the
theorem still owes the second leg.

|Grade 2ii
|`PWG-2ii`
|Both of the policy's legs, Rocq *and* Lean, count. A non-DTT witness, such
as Isabelle/HOL, is the separate tag `+foundation-diverse`. It is no
longer the condition for 2ii, and it never stands in for a leg.

|Grade 1
|`PWG-1`
|Claim-gated. It needs a current receipt from a pinned, headless,
isolated checker for every witness, at the exact source commit. AXLE,
`isabelle server` and coq-lsp are examples, not requirements. Any
"verified" or "machine-checked through …" claim needs these receipts, and
a regression drops the grade.

|§6 `Superseded` / `Regressed`
|Receipt lineage
|Recorded on the receipt as `state: superseded\|regressed`, with the
reason. The status vocabulary stays closed.

|§6 "no percentages"
|Census rule
|Grade counts are published with their denominator, with the lower and
`ungraded` rungs named. Never as a percentage.
|===

Always write the `PWG-` prefix. Mathesis also uses "grade" for its
per-verb coaptation grades (`.machine_readable/coaptation/`), and the
estate uses it for CRG, TRG, ARG and FRG. None of those is a PWG.

[IMPORTANT]
.Aeneas translations as a default learning route for ECHIDNA (owner direction 2026-11-09)
====
*Default.* First-party Rust that is verified with Creusot/Pearlite and
Verus (PROOF-POLICY §1.2) is also translated with *Aeneas* (via Charon) into
a Lean or Rocq model by default, starting with the security cores. A repo
opts out by saying so in its proof-status file. The owner names the
occasions where it does not apply.

*Purpose.* The translations are a corpus for ECHIDNA, not proof evidence.
Each translation pairs:

* the Rust source;
* its Creusot and Verus contracts;
* the Aeneas model;
* where one exists, the Agda theorem and its Rocq or Lean recheck.

ECHIDNA learns from these pairs how statements correspond across systems.
That is the groundwork for *mathematical-object arbitration*: deciding
whether two artefacts in different systems state the same thing, which is
the estate's equivalence-as-identity through-line. The corpus also exercises
ECHIDNA's cross-prover exchange (OpenTheory, Dedukti) on real estate code.

*What it does not change.*

* *No proof status rises.* The theorem about an Aeneas model may be
`PROVEN`. The correspondence between the model and the Rust (Aeneas's
translation) is a separate `ASSUMED` row (PROOF-POLICY §4.1). A Creusot or
Verus result on the code itself is still what establishes implementation
correctness.
* *Backend axioms.* Aeneas's Rocq backend carries an axiom from which
`False` is derivable (its `mk_array` axiom, Aeneas issue #1116). Its Lean
backend depends on Mathlib, which §2 rules out for theory rechecks. Neither
backend's output may stand as a theory witness or count toward a PWG.
Corpus use is unaffected, because nothing in the corpus is counted.
* *Evidence stays home.* Each translation and its receipt live in the home
repository. Mathesis catalogues them as correspondence records, not as
receipts of proof.

*Policy gap.* PROOF-POLICY §4.1 currently allows Aeneas "only where Rust
code implements a theorem proved in Agda". Making it a default, even for
corpus use, needs an amendment in `metadatastician/standards`. File it
together with the ATS2 amendment (also owner direction 2026-11-09). Until
then, translations outside §4.1's scope are corpus artefacts only and are
recorded as such.

*Related direction (design open).* Mathesis becomes the shared, canonical
centre for this record. Each participating repository keeps a local copy
that is attested by its deed and kept in line by k9 and coordination
runners. Any drift from, or attempt to change, the canonical record raises
an alert. Fable's restart session sets the mechanism.
====

== Original working brief (preserved)

[literal]
....
MATHESIS — Estate-wide Mathematical Knowledge Architecture

Mission
Re-evaluate and substantially improve the architecture of hyperpolymath/mathesis. Mathesis is intended to become the mathematical knowledge commons, proof-discovery atlas, and research-orientation system for a large, heterogeneous, multi-organisation software estate.

It must serve humans, researchers, mathematicians, developers, coding agents, theorem-proving agents, and automated verification systems. The objective is to map out exact proof states, track translation pipelines across distinct logical foundations, and eliminate dependence on the owner's memory without turning Mathesis into a monolithic proof repository. The original repositories remain the sovereign territory of their own mathematics.

1. Mandatory Initial Audit
Read the actual Mathesis repository before proposing changes. Start with README.adoc, docs/catalogue/catalogue.adoc, the scripts/census/ tools, the repository deed, and relevant CI workflows.

Distinguish genuine architectural limits from deliberate simplifications.

Do not discard the working census or its reproducibility simply to create a more elaborate directory layout.

2. Estate Discovery, Authority, and Incremental Indexing
Mathesis must discover repositories across relevant owners, forges, and mirrors. Determine which source is authoritative for repository identity, clade/lineage (e.g., gv-clade-index), project membership, and verification receipts.

The "Cold Start" Protocol: The indexing architecture must support incremental caching. A single repository push must update its own sub-graph and theorem states without forcing a multi-hour rebuild of the entire 400+ repository estate.

Identity: Do not become a competing canonical registry for identities already owned by gv-clade-index. Use stable identifiers, aliases, and source pointers.

3. Scope of Mathematical and Engineering Material
A repository need not contain a .agda or .lean file to belong in Mathesis. Discover mathematics appearing in compilers, databases, knot theory, topological simulations, and game engines.

The estate explicitly divides into a Theory Path and an Engineering Path. Mathesis must track both:

Theory Path: Pure mathematical formulation, topological proofs, and strict foundational verification (Agda, Rocq/Coq, Lean 4, Isabelle/HOL).

Engineering Path: Applied invariants and bounded runtime verification. Mathesis must track:

Idris2: For verified ABIs and strict type-driven design boundaries.

Rust (Creusot) & Ada (SPARK): For memory-safe, mission-critical systems. (Note: These compile to the Why3 intermediate verification language. If Why3's automated SMT solvers fail, the resulting proof witnesses must be exported to Rocq or Isabelle for manual closure).

Experimental Engineering Verification: Recognize and track early-stage verification bounds for newer languages. This specifically includes Apodeixi.jl (Julia for data), quintessence (Elixir for web/concurrency/fault tolerance), atoma (Zig for FFIs/APIs), and bactrian (OCaml for compilers and data processing).

4. Navigation Views
Provide four complementary, generated navigation views:

A. Alphabetical Mathematical Atlas: A–Z index of concepts, definitions, and aliases linking to their source proofs.

B. Mathematical Subject Hierarchy: Standardized classifications (e.g., MSC2020) for interdisciplinary work.

C. Project and Research Clusters: Navigable clusters spanning repositories (e.g., FSinFS, Echo/epistemic research, QuandleDB, eNSAID).

D. Estate and Provenance View: Browse by organization, proof assistant, verification grade, and maturity status.

5. The Verification Pipeline: Graded Proof Architecture
Mathesis must rigorously categorize theorems through a strict verification grading system. This tracks a proof from iterative theory down to API-verified cross-system certainty.

Grade 3 (Iterative & Tentative Formulation): Prototyped and iteratively constructed in Agda. This relies on strict solver flags (e.g., --safe --erasure) or topological geometry (e.g., Full --cubical for knot/Conway problems). A proof is Grade 3 if it type-checks locally in Agda but has not been translated to an independent foundational system.

Grade 2 (Proof Witness Translation): The Agda proof is translated into a highly rigid, independent foundational proof language.

Grade 2i (Single Translation): The proof witness is translated to ONE alternative foundational system (e.g., Lean 4 or Rocq).

Grade 2ii (Dual Translation for High-Assurance): The proof witness is translated into TWO fundamentally distinct logical architectures. Note on Prover Families to avoid foundational blind spots: Agda, Rocq, and Lean 4 all belong to the Dependent Type Theory (DTT) / Calculus of Inductive Constructions family. To achieve true foundational diversity for a Grade 2ii theorem, the second translation must target a non-DTT system like Isabelle/HOL (which relies on Higher-Order Logic/LCF-architecture).

Grade 1 (Machine-Checked via Verified API): The translated proof witnesses successfully compile in headless, isolated CI environments via verified checker APIs. This requires passing the Axiom Lean Engine (AXLE) API for Lean 4, isabelle server instances for Isabelle/HOL, or internal coq-lsp REST APIs for Rocq.

6. Epistemic Precision, Versioning, and Deprecation
Do not flatten proof confidence into a percentage. Record exactly whether a result is Open, Claimed, Grade 3, Grade 2i/ii, or Grade 1.

Axiom Tracking: Track whether a result depends on unverified postulates, #print axioms (Lean), Print Assumptions (Rocq), or pinned library versions.

Versioning and Regressions: A theorem proven in commit A may break in commit B. Mathesis must track the exact Git commit hash of the verification receipt. Introduce Superseded and Regressed statuses to flag previously Grade 1 proofs that no longer compile against the HEAD of their source repositories.

7. Search, Access Control, and Knowledge Retrieval
Use the simplest useful working architecture (e.g., Canonical versions → deterministic generated SQLite/FTS5 index).

Access Boundaries & Row-Level Security: Do not treat a private repository as absent merely because the scanner cannot read it. Conversely, the index query layer must enforce access-control natively (e.g., via clearance tokens or segregated databases) so that a public Mathesis catalog never leaks private repository titles, theorem statements, or WIP mathematical metadata.

8. Agent Interfaces and Write-Back Correction
Design a stable entry point for coding agents (e.g., "Orient me to the mathematical estate," "Prepare a token-budgeted context pack").

LLM Hypothesis Tagging: Any missing mathematical bridge or dependency suggested by an LLM must be strictly tagged as LLM-Hypothesized (Unverified).

Correction Pipeline: Agents must not have direct write-access to mutate the canonical SQLite index. Provide a strict "write-back" or "nomination" API where agents can submit discovered broken links, missing verification receipts, or false positives for human or CI-gated review.

9. Dogfooding Investigations
Build and measure at least three substantive experiments to prove the architecture:

Experiment A (FSinFS): Discover existing theorems, trace them through the pipeline, and output missing proof obligations.

Experiment B (Quandles & Knots): Connect abstract KnotTheory.jl ideas to Full Cubical Agda topological foundations.

Experiment C (Cross-Boundary Proof Identity): Verify that Mathesis correctly maps a Grade 3 Agda specification to a Grade 1 Lean/Isabelle proof witness, and connects both to their engineering implementations (e.g., Rust/Creusot).

10. Directory and Repository Architecture
Develop and evaluate candidate architectures. Consider a structure like:

registry/ — Canonical records and Grade 1-3 receipts.

schemas/ — Validated record schemas.

docs/atlas/ — Generated A-Z, subject, project, and estate views.

tools/ — Extraction, validation, and incremental indexing logic.
Keep original proofs in their respective home repositories.

11. Licensing, Reproducibility, and Trust
Use MPL-2.0. Do not copy entire external mathematical libraries or papers merely to index them; prefer source references. Reject silent index drift, duplicate proof inflation, and false positive verification claims. The system should report unresolved or unavailable evidence plainly.

12. Delivery Stages
Stage 0: Ground-truth audit and CI review.

Stage 1: Architecture and schema decision.

Stage 2: Minimal working catalog (small vertical slice with generated views).

Stage 3: Estate discovery with incremental refresh.

Stage 4: Proof-level indexing (extracting Grade 1-3 statuses and assumptions).

Stage 5: Retrieval evaluation (execute Dogfooding experiments).

Stage 6: Agent interoperability (read APIs and write-back nomination).

Stage 7: Wider mathematical atlas (external links and unformalized concepts).

13. What Not To Do
Do not replace the current working census with an unfinished system.

Do not assume all mathematics is located in .agda or .lean files.

Do not invent missing repository identities or mathematical relationships to create a tidy taxonomy.

Do not allow agent-generated evidence to count as independent corroboration.

Do not treat embedding similarity as mathematical equivalence.

Do not build a new theorem prover or a custom graph database unless strictly required by performance bottlenecks.

14. Required Final Handover
Produce a substantial report detailing the current limitations, the recommended schema, the exact relationship to tools like gv-clade-index and AXLE, a phased roadmap, and the execution results of the Dogfooding experiments.

Finish with a clear answer to: What can a completely unfamiliar mathematical researcher or coding agent now discover, verify, and understand using Mathesis that they could not reliably discover before?
