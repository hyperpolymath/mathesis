== Verdict in one page

*Where Mathesis stands.* The facts below were measured on `main` at
`8ee6354` (2026-11-10). <<measured>> gives the command or file for each.

* Mathesis has real, working parts. A census reads 505 repositories, and a
  catalogue lists the 248 that have proof files. Three atlas views are
  generated from the catalogue rows. A pilot registry pins 17 claims. One
  theory theorem is proved in three provers. An applied-systems area exists.
* These parts are a small share of the tree. Of 539 tracked files, 52 exist
  only in Mathesis and 23 more were changed after the mint. The other 464 come
  from the RSR template unchanged, or changed only by the mint's name pass.
* The declared golden path, `just test && just quality`, checks template
  stubs only. It checks no Mathesis part, and no workflow runs it.
* Main CI is green. Four checks fail when a person runs them, and CI runs none
  of them. They are the catalogue drift check, the arrival-pack check, the
  coaptation check and the AI-install check.
* The deed, the six contractiles and most status documents still describe the
  template. The north-star contract lists the template's goals.
* 17 pull requests are open. Each one conflicts with `main`. At least six
  repeat a fix that `main` already has.
* The public data names 40 private repositories. The architecture document
  says that private metadata must not be published.
* Two programs derive Proof Witness Grades by different rules: the Mathesis
  registry tool and the reader that the proof policy names as normative.
* Mathesis records the grade of its own theorem in prose only. It keeps no
  machine-readable receipt, and its own registry does not list the theorem.

*What Mathesis is.* Mathesis is the maths section of the estate. It keeps an
atlas of the mathematics in other repositories, the theory that no single
system owns, and methods that apply mathematics to decisions. One rule binds
the three: each statement carries its evidence, and Mathesis derives status
from that evidence. It does not assert status.

*How it fits the estate.* The standards repository prescribes. The home
repositories prove. Mathesis describes.

*What to do.* Six stages, each made of small work orders (<<work-orders>>):

. Stage 0 stops the conflict between pull requests.
. Stage 1 closes the soundness holes.
. Stage 2 makes one data pipeline with one vocabulary.
. Stage 3 makes the deed, the contracts and the documents tell the truth.
. Stage 4 gives each of the three shelves its rule and its first content.
. Stage 5 scales the derived registry across the home repositories.

The owner's decisions are in <<decisions>>.

=== Findings

Each finding states a fact, its evidence and its consequence.

[[f-1]]F-1. The golden path does not test Mathesis::
`just test` runs `idris2 --typecheck src/interface/abi.ipkg` and
`zig build test` in `src/interface/ffi`. `just quality` adds
`zig fmt --check`. These files are template stubs. The census, atlas, registry
and proof checks are separate recipes. No workflow runs `just test` or
`just quality`. The deed's `(anchor (golden-path))` therefore promises a check
that says nothing about this repository.

[[f-2]]F-2. Four checks fail and CI does not run them::
See <<gate-results>>. The duplicate catalogue row came from two merged pull
requests that changed the same generated file. A check that CI does not run
cannot protect `main`.

[[f-3]]F-3. The descriptive record describes the template::
* Deed: `(manifest :purpose)` says "Canonical RSR ... template".
  `(meta :type)` says `library`. `(anchor (implementation-policy))` allows
  Rust, Idris2 and Zig and does not name the JavaScript that the atlas and
  registry use. `(anchor (semantic-authority-files))` names four files that do
  not exist. `(ecosystem :not)` is empty. `(variant (paths :added))` is empty.
* Contractiles: the `intend` contract lists `repo-initialization` and four
  more template goals. No contract states a Mathesis invariant.
* Status: `TEST-NEEDS.adoc` records CRG grade C as "ACHIEVED 2026-04-04", a
  date before this repository existed. `READINESS.adoc` is an unfilled form.
  `ROADMAP.adoc` keeps the template milestones. `PROOF-NEEDS.adoc` lists the
  template's seven ABI and typing obligations.
* Documents: `docs/EXPLAINME.adoc` is titled "RSR Template Repo - Explainme".
  `docs/usage.adoc` shows a service that listens on port 8080.
  `docs/AFFIRMATION.adoc` is an unsigned form.
* The name pass damaged some sentences. `PROOF-NEEDS.adoc` says "These proofs
  come from the mathesis". The `dust` contract forbids "references to mathesis
  in generic template files".

[[f-4]]F-4. The capability profile is empty, and two gates disagree::
The canon decides which template modules a repository carries by its declared
capabilities. Mathesis declares none. With an honest profile
(<<wo-3-2>>), the canon checker reports seven vestigial modules:
`src/interface/ffi/`, `src/interface/Abi/`, `src/interface/generated/`,
`benches/`, `build/container/Containerfile`, `rust-ci.yml` and `release.yml`.
The local `just validate-rsr` requires three of these directories in every
repository. The two gates cannot both pass. The cause is in the template.
+
The canon checker also compares `(manifest :project)` with the deed's
`:canonical-name`, letter for letter. The deed has "Mathesis" in one and
"mathesis" in the other, so the checker reports a missing baseline manifest.

[[f-5]]F-5. Two derivations of the grade exist::
PROOF-POLICY §8.5.1 names `readProofReceipt` in the standards repository as
"the normative definition of the profile's fields, vocabularies and
derivation". It says that Mathesis reads receipts through it. The Mathesis
tool `scripts/registry/claims-registry.mjs` has its own parser and its own
rules. The rules differ in three places:
+
* The canon counts a recheck leg only with a `proven` token, a `transported`
  or `re-proved` route, the state `RECONCILED` and a current receipt. The
  Mathesis tool counts each leg whose state is `RECONCILED`.
* The canon requires a current Agda receipt and the state `AGDA-VERIFIED`. The
  Mathesis tool reads one `:flags` field and the Agda token.
* The canon derives `PWG-1`. The Mathesis tool does not.

[[f-6]]F-6. Mathesis does not yet keep the rules of a home repository::
THY-1 has a careful prose record in `docs/status/PROOF-STATUS.adoc`. The
record has gaps that the same file and the roadmap name:
+
* No receipt deed exists under `verification/receipts/` (PROOF-POLICY §8.5.1).
* The registry does not list `hyperpolymath/mathesis#THY-1`.
* No CI lane runs the Rocq leg or the Lean leg.
* `scripts/check-proofs.sh` passes a Rocq file with `Admitted` and a Lean file
  with `sorry`.
* The Agda lane installs Agda from the distribution package. PROOF-POLICY §6
  requires a `deviation` record for that, and none exists.

[[f-7]]F-7. One register is written by hand::
`docs/status/CROSS-PROVER-RECONCILIATION.adoc` calls itself a working policy.
PROOF-POLICY §2.2 has since adopted that vocabulary, so the policy text is now
a copy. The same file holds a register of grades that a person typed. The
registry exists so that nobody types a grade.

[[f-8]]F-8. The data layout causes the pull request conflicts::
* Each data file is one line of JSON. Two pull requests that change two
  different rows conflict on that line.
* A row has no source commit and no census date. A reader cannot tell a fresh
  row from an old one.
* The atlas test, the atlas README and the main README state the row count as
  a literal number. Each refresh must edit them.
* No rule names one writer for the census data. On 2026-11-09 many sessions
  refreshed rows at the same time.
* The deed's `(coverage)` and `(debt)` clauses are empty, so no session could
  see the work of another.

[[f-9]]F-9. Private names are public::
`repos.json` lists 40 repositories with `"visibility":"private"`.
`unreachable.json` and the "Not reached" section of `catalogue.adoc` repeat
the names. `README.adoc` names one of them. `docs/architecture.adoc` says
"private metadata must not be published". The architecture brief says a
public catalogue must not leak private repository titles.

[[f-10]]F-10. Three proposals overlap, and the canon settled part of them::
Issue 28, `proof-receipts-as-data.adoc` and ADR 0004 each propose how
receipts become data. PROOF-POLICY §8.5.1 now fixes the receipt format, its
conventional path and its reader. Each proposal still reads as open.

[[f-11]]F-11. A ruling about Mathesis is not recorded in Mathesis::
The owner ruled on 2026-11-09 that the token-lattice theory lives in Mathesis
(decision D-10 of the ECHIDNA proof-route plan in the standards repository).
On `main`, no Mathesis file records the ruling. An open, conflicting pull
request carries it.

=== What works and must stay

* The census is reproducible, and it states its own limits in plain words.
* The atlas refuses a row whose repository is not public. Its tests include

* A registry record holds no grade. It pins a commit and a receipt digest.
* The THY-1 record is a model: checker versions, invocations, file digests,

  It records the failed Dedukti route as `BLOCKED` and describes a seven-line

* `docs/standards/AUTHORITY.adoc` and `docs/architecture.adoc` state the

* The applied-systems area has its own evidence vocabulary, and it keeps

[[identity]]
== The proposed identity

=== In brief

Mathesis is the maths section of the estate. It keeps an atlas of the
mathematics in other repositories, the theory that no single system owns, and
methods that apply mathematics to decisions.

=== Three verbs

[cols="1,2,4",options="header"]
|===
|Verb |Who |What

|Prescribe
|`metadatastician/standards`
|It says what must be proved and how (PROOF-POLICY, the requirements master
list).

|Prove
|Each home repository
|It holds the proof and the receipt. It owns the theorem and its evidence.

|Describe
|Mathesis
|It says what is proved, where and how strongly. It derives each answer from
the home's receipts.
|===

In the estate's own terms, Mathesis is the mathematical *descriptile* of the
estate and the standards repository holds the *contractile*. A report that
compares the two is the estate-level form of coaptation.

Mathesis is also a home repository for its own theory. In that role it obeys
each rule that it checks in others.

=== IS and IS NOT

Mathesis *is*:

* the index that answers "where does that proof live, and what supports it?";
* the home of theory that an estate rule or vocabulary depends on and that no
  single system owns;
* the canonical place for bridge records that cross repositories
  (<<centre>>, proposed);
* a place for reusable methods that apply mathematics to decisions.

Mathesis *is not*:

* a prover or a proof kernel. The home repository's checker decides.
* the proof policy. PROOF-POLICY decides.
* the identity registry. `gv-clade-index` decides.
* the map of the type family. `nextgen-typing` coordinates that map and its
  glossary.
* a copy of other repositories' proofs or receipts.
* a grade authority. It derives a grade and does not assign one.
* a store for private or organisation-specific case material.
* the RSR template. The template is its lineage only.

=== The spine: one relation, four record kinds

The manifesto defines assurance as "a disciplined relationship among a claim,
the evidence offered for it, the model in which that evidence has force, the
residual uncertainty, and an authority accountable for the decision". Mathesis
uses that relation as its record model.

|Evidence

|The home's receipt deed

|Model

=== Three shelves

[cols="1,3,2,3",options="header"]

[[centre]]
== The bridge centre (proposed mechanism)

The architecture brief records an owner direction of 2026-11-09. Mathesis
becomes the canonical centre for the correspondence record. Each
participating repository keeps an attested local copy, and drift raises an
alert. The brief leaves the mechanism open. This section proposes one.

The estate already has a word for one such record: a *bridge*. PROOF-POLICY
§2.2 uses it ("a checked bridge or justified statement correspondence"). The
owner's research note on types, tropes and identity
(`hyperpolymath/vcl-ut`, `docs/research/TYPE-TROPE-IDENTITY-SPACES.adoc`)
defines it. This plan uses the word with that meaning.

=== Principle

Evidence is local. A bridge has two ends.

A home repository can check its own proofs, so it owns its evidence. A bridge
relates two artefacts, and the two can be in two repositories. Examples are
an Agda statement and its Lean restatement, or a theorem and the code that
implements it. If one end keeps the record, the other end can change without
notice. So the centre keeps the record, and each end keeps an attested copy.

This principle keeps the receipt rule intact. Proof status still comes from
the home's receipts. The centre records only the relation and points at the
evidence in each home.

The centre does not decide how the type disciplines relate. `nextgen-typing`
holds that map (`docs/TYPE-CONNECTIONS.adoc`) and its decisions. A Mathesis
bridge records the evidence for one pair of artefacts.

=== Rules that each bridge obeys

The rules come from the research note. A bridge is "a partial and potentially
many-to-many, direction-sensitive relation, not an assumed coercion or
equivalence".

* It names its *criterion*: what "the same" means for this bridge, and for
  which observer.
* It states what it *preserves* and what it *forgets*.
* It has a *direction*.
* It claims no universal identity. Two artefacts are the same under a named
  criterion, or they are not related by this record.
* Equal names prove nothing. The estate has an example: an Agda record and a
  Lean structure are both named `ResourceAlgebra`, and their laws differ.

=== The record

One record for each bridge, in `docs/atlas/claims/bridges.jsonl`:

* an identifier;
* two endpoints, each with repository, commit, path, name, system and the
  blob digest of the file;
* the criterion and the direction;
* what the bridge preserves and what it forgets;
* the relation: `same-statement`, `refinement`, `conditional-transport`,
  `countermodel` or `unassessed`;
* the §2.2 correspondence state;
* the basis: `read`, `generated`, `transported` or `proved`;
* a pointer to the comparison record in a home repository;
* the residual assumptions;
* who proposed it, a person or an agent, and who reviewed it.

A record that an agent proposed stays `unassessed` until a person reviews a
comparison that a home repository holds. The record holds no token and no
grade.

The survey found three practices for that review:

* `MetaManifold-Evidence` and `hvn-dehallucinator` keep a leg
  `BRIDGE-PENDING` until the owner reviews the comparison.
* `lintel` records `RECONCILED` and says that the comparison is provisional
  until the owner reviews it.
* `nextgen-typing` (XP-1) and Mathesis (THY-1) record `RECONCILED` with no
  such note.

The bridge record names the reviewer, so the three cases cannot look the
same.

=== What the centre computes

* *Classes under one criterion.* The centre composes the bridges that share a
  criterion and that the records declare composable. It lists the classes
  that result. A class means "the same under this criterion". The concept
  view of the architecture brief can list these classes. Nobody writes that
  view by hand.
* *Order.* `refinement` bridges give an order between classes.
* *Contradictions.* A `countermodel` between two artefacts that a chain of
  bridges joins, under the same criterion, fails the check.
* *Five different absences.* When no bridge exists, the view says which case
  holds: refuted, not yet proved, not enough evidence, forbidden, or not
  defined. The research note asks for this distinction.

This is the manifesto's phrase "identity defined by equivalence rather than
asserted", made into a computation that always names its criterion.

=== The lock

The estate already has one pattern for a canonical centre with pinned
copies: the canon lockstep in the deed's `(canon)` clause. The proposal uses
the same pattern.

. Mathesis publishes a lock file. For each participating repository, the lock
  gives the digest of the records that name it. This set is the repository's
  *slice*.
. Each participating repository keeps its slice as a file and records the
  slice digest in its deed.
. A k9 contract in the home compares the local slice with the lock at the
  pinned Mathesis commit. A difference fails the home's gate.
. A check in Mathesis compares each endpoint's blob digest with the home's
  current tree. A changed file marks the record `stale` and fails the check.
. A pull request that changes a record must name the home commits that hold
  the evidence. The check lists each affected repository.

Blob digests make a record survive commits that do not touch the file. A
commit that changes the statement makes the record stale, which is correct.
A stale record is a question about identity through time. A new comparison
answers it. A digest does not.

=== Order of work

. The home lands the proof, the receipt and the statement comparison.
. Mathesis records the bridge and releases the lock.
. The home pins its slice.

The centre derives the bridges inside one home from that home's receipt: the
legs of one claim are joined there already. It records by hand only the
bridges that cross repositories.

Two pilots are ready. The first is a squeakwell recovery-ladder row, whose
Agda, Rocq and Lean artefacts are in three repositories. The second is the
open bridge between the Agda `ResourceAlgebra` of `resource-algebra` and the
Lean structure of the same name in `tropical-types`.

[[no-rewrite]]
=== Why the history is not rewritten

A rewrite of the history would add little and cost much.

* It cannot remove the names from public view. They have been public since
  2026-10-26. They are in each mirror, in each clone and in the pull request
  refs, which a force-push does not remove.
* The public standards repository names at least one of the same private
  repositories.
* It changes each commit identifier. Other repositories cite Mathesis by
  commit, and the THY-1 record in `PROOF-STATUS.adoc` cites two source
  commits. Those citations would point at nothing.
* It breaks each clone, each mirror and each open pull request.

If one name is sensitive, the effective remedy is to rename that private
repository. The published name then points at nothing.

== What this plan does not do

* It does not move, copy or regrade any proof in another repository.
* It does not change PROOF-POLICY or any other canon text.
* It does not register Mathesis in `gv-clade-index`. Registration is the
  owner's act. The index at `539dd61` has no entry for Mathesis.
* It does not replace the working census before a tested replacement exists.
* It does not edit a licence.
